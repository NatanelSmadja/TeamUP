# דוח אבטחה ל־TEAMUP

תאריך בדיקה: 20 בספטמבר 2026

## מצב תיקון

הממצאים הטכניים בדוח טופלו במיגרציות `046` ו־`047` ובקוד היישום:

* נחסמה עריכת `is_system_admin` ושאר שדות המערכת דרך הפרופיל.
* תוקנה הפרדת הפעילות והקבוצות ב־RLS.
* פונקציות פנימיות וטריגרים נסגרו בפני `anon` ובפני קריאה ישירה שאינה נדרשת.
* בוטלו כל הרשאות הכתיבה הרחבות ו־`TRUNCATE` של `authenticated`; כתיבות הדפדפן עוברות דרך RPC מאומתים, למעט סימון `is_read` בלבד בהתראות.
* חשיפת פרופילים צומצמה לעצמי, למנהל מערכת ולחברים בקבוצה פעילה משותפת.
* היסטוריית המיגרציות יושרה מול המסד עד `047`.
* מדיניות הסיסמה הועלתה ל־10 תווים עם אותיות ומספרים ונדרש אימות מחדש בשינוי סיסמה.
* חבילות npm עודכנו ו־`npm audit` חזר עם אפס חולשות.
* נוספו CSP וכותרות אבטחה, CORS של ההתראות הוגבל, ויעדי Push הוגבלו לאותו origin.

הגנת HaveIBeenPwned של Supabase נשארה כבויה משום שה־Management API דחה את ההפעלה בפרויקט שאינו בתוכנית Pro. זו מגבלת חבילה חיצונית; שאר מדיניות הסיסמה הוקשחה.

## מסקנה

בבדיקה המקורית נמצאו שתי פרצות קריטיות שניתנו לניצול באמצעות קריאות ישירות ל־Supabase, בלי לשנות את קוד הממשק ובלי לפרוץ סיסמה:

1. משתמש מחובר יכול לעדכן בפרופיל של עצמו את `is_system_admin` ולהפוך למנהל מערכת.
2. משתמש שחבר בקבוצה אחת יכול לקרוא אירועי פעילות של קבוצות אחרות בגלל שגיאת RLS.

שתי הפרצות תוקנו לאחר הבדיקה, כמפורט בסעיף מצב התיקון.

## היקף הבדיקה

נבדקו קוד ה־React, מיגרציות SQL, פונקציות `SECURITY DEFINER`, מדיניות RLS בפועל במסד המקושר, הרשאות `anon` ו־`authenticated`, סודות וקבצי env, פונקציית ה־Edge של ההתראות, הגדרות Vercel, תלויות npm והתרעות האבטחה החיות של Supabase.

הבדיקה הייתה קריאה בלבד. לא נשלחו בקשות ניצול שמשנות נתונים ולא נעשה מבחן עומס.

## ממצאים קריטיים

### 1. הסלמת הרשאות עצמית למנהל מערכת

מדיניות `profile owner update` מאפשרת למשתמש לעדכן את כל העמודות בשורה שלו. ההרשאה החיה כוללת `UPDATE` על `is_system_admin`, `base_rating`, `lifecycle_status`, `archived_at` ושדות מערכת נוספים. הטריגר היחיד על `profiles` רק מעדכן `updated_at`.

הפונקציה `is_system_admin()` סומכת ישירות על הערך הזה. לכן משתמש רגיל יכול לנסות לשנות את השדה שלו ל־`true`, ולאחר מכן לעבור בדיקות הרשאה של פונקציות ניהול המערכת.

מקור: `supabase/migrations/001_initial.sql:276`, `supabase/migrations/010_signup_positions_system_admin.sql:81`.

תיקון נדרש:

1. לבטל מיד הרשאת עדכון של משתמשים על כל שדות המערכת.
2. לתת `UPDATE` רק לעמודות פרופיל שהמשתמש רשאי לערוך.
3. להוסיף טריגר הגנה שמונע שינוי של שדות רגישים גם אם הרשאה תיפתח בטעות בעתיד.
4. לבדוק ביומן אם משתמשים שאינם מורשים כבר קיבלו `is_system_admin=true` או שינו דירוג בסיס ומצב חשבון.

### 2. דליפת פעילות בין קבוצות

המדיניות נכתבה עם `gm.group_id=group_id`. במסד החי PostgreSQL פירש אותה כ־`gm.group_id=gm.group_id`, תנאי שתמיד נכון. כתוצאה מכך, כל משתמש בעל חברות פעילה בקבוצה כלשהי יכול לקרוא את `activity_events` של כל הקבוצות.

מקור: `supabase/migrations/006_teamup_v2.sql:44`.

תיקון נדרש: לתת לטבלה החיצונית alias מפורש ולהשוות `gm.group_id` אל `activity_events.group_id`, ואז לבצע בדיקת בידוד עם שני משתמשים בשתי קבוצות שונות.

## ממצאים בחומרה גבוהה

### 3. פונקציות בעלות הרשאות בעלים פתוחות לאורחים

במסד החי נמצאו 53 אזהרות על פונקציות `SECURITY DEFINER` הניתנות להרצה על ידי `anon`, ו־95 עבור משתמשים מחוברים. חלק מהפונקציות מיועדות להיות RPC ציבורי ומבצעות בדיקה פנימית, ולכן המספר לבדו אינו אומר שיש 148 פרצות. עם זאת, נמצאו פונקציות בעייתיות בפועל:

* `notify_group(...)` פתוחה ל־`anon` ול־`authenticated` ואינה בודקת את הקורא. מי שמכיר מזהה קבוצה יכול ליצור הודעות שרירותיות לכל חבריה ואף לגרום לשליחת Push.
* `log_activity(...)` פתוחה ל־`anon` ול־`authenticated` ואינה בודקת את הקורא. ניתן לזייף אירועי פעילות, שחקן מבצע ותוכן.
* `match_goal_reporting_open(...)` פתוחה לאורחים ללא צורך ברור.
* פונקציות טריגר רבות פתוחות כ־RPC למרות שהן אמורות לפעול רק מטריגרים.

מקור: `supabase/migrations/004_realtime_members_flexible_teams.sql:38`, `supabase/migrations/006_teamup_v2.sql:53`.

תיקון נדרש: לבצע `REVOKE EXECUTE` מ־`PUBLIC`, מ־`anon` ומ־`authenticated` לכל פונקציית טריגר או helper פנימי; להעניק הרשאה מפורשת רק ל־RPC שהממשק באמת קורא; ולהשאיר בכל RPC בדיקת `auth.uid()` והרשאת קבוצה לפני פעולה.

### 4. חשיפת כל הפרופילים לכל משתמש מחובר

המדיניות `profiles visible to authenticated` משתמשת ב־`USING (true)`. כל חשבון מחובר יכול לקרוא את כל הפרופילים, כולל תאריך לידה, דירוג בסיס, מצב חשבון, זמן ארכוב והסימון מי מנהל מערכת.

מקור: `supabase/migrations/001_initial.sql:275`.

תיקון נדרש: להפריד בין פרופיל פרטי לבין כרטיס שחקן ציבורי. פרטים רגישים יהיו זמינים רק לבעל החשבון ולמנהלים מורשים; חברי קבוצה משותפת יקבלו רק שדות משחק נחוצים.

### 5. הרשאות עדכון רחבות מדי בקבוצות ובמשחקים

`groups admin update` מאפשרת למנהל קבוצה לעדכן את כל שורת הקבוצה, כולל שדות שאמורים להיות בשליטת בעלים או מערכת. אין טריגר שמגן על `owner_id`, קוד הזמנה או מצב מחזור החיים.

`matches permitted update` מאשרת עדכון של כל השורה למי שיש לו אחת מההרשאות `edit_match`, `close_registration` או `open_ratings`. כך הרשאה נקודתית לסגירת הרשמה עלולה לאפשר שינוי תאריך, קיבולת, סטטוס ושדות נוספים באמצעות REST. קיים טריגר שמגן על שינוי כותרת, אך לא על שאר העמודות.

מקור: `supabase/migrations/001_initial.sql:278`, `supabase/migrations/003_permissions_workflow.sql:11`, `supabase/migrations/041_rename_match.sql`.

תיקון נדרש: להעביר פעולות רגישות ל־RPC ייעודיים, להסיר עדכון ישיר רחב, ולהוסיף הגנות ברמת עמודה או טריגרים לשדות מערכת.

### 6. היסטוריית המיגרציות אינה תואמת למסד

במסד רשומות כמוחלות רק מיגרציות `001` עד `031`, בעוד שהסכמה החיה כבר כוללת חלקים מ־`032` עד `045`. הפעלה עתידית של `supabase db push` עלולה לנסות להריץ שוב מיגרציות, לדרוס פונקציות ומדיניות, או להיכשל באמצע פריסה.

תיקון נדרש: לבצע reconciliation מסודר של היסטוריית המיגרציות מול הסכמה החיה לפני כל פריסה נוספת, ולוודא שכל תיקון אבטחה נרשם כמיגרציה חדשה אחת וברורה.

## ממצאים בחומרה בינונית

### 7. סיסמאות חלשות והגנת סיסמאות שדלפו כבויה

הממשק מאפשר סיסמה בת שישה תווים. Supabase Advisor מאשר שהגנת Leaked Password Protection כבויה.

תיקון נדרש: להעלות את המינימום ל־10 או 12 תווים בצד Supabase ובממשק, להפעיל בדיקת סיסמאות שדלפו, ולשקול MFA לפחות למנהלי מערכת ובעלי קבוצות.

### 8. שתי חולשות production בתלויות npm

`npm audit --omit=dev` מצא שתי חולשות ברמת High ב־`react-router` וב־`react-router-dom`. האזהרה עוסקת ב־RSC, והיישום הנוכחי הוא SPA רגיל, כך שהחשיפה המעשית כנראה נמוכה יותר, אך יש עדכון זמין ויש לבצעו. בבדיקה המלאה נמצאו גם שש חולשות נוספות בתלויות build ופיתוח.

תיקון נדרש: לעדכן לגרסה מתוקנת, להריץ build ותרחישי ניווט, ואז להריץ שוב `npm audit`.

### 9. חסרות כותרות אבטחה בדפדפן

`vercel.json` מכיל rewrite בלבד. אין CSP, `frame-ancestors`, HSTS, `X-Content-Type-Options`, `Referrer-Policy` או `Permissions-Policy`.

העדר CSP מגדיל את הנזק האפשרי של XSS עתידי, במיוחד מפני שסשן Supabase נשמר בדפדפן.

תיקון נדרש: להוסיף headers ב־Vercel עם CSP שמתירה חיבור רק לדומיין Supabase ולשירותים שבשימוש, לחסום embedding, ולבדוק שההתראות וה־Realtime ממשיכים לעבוד.

### 10. הרשאות בסיס רחבות מדי לטבלאות

לטבלאות רבות קיימות הרשאות CRUD רחבות עבור `anon` ו־`authenticated`, וההגנה נשענת בעיקר על RLS. RLS פעיל בכל הטבלאות הציבוריות שנבדקו, אך טעות מדיניות אחת, כפי שכבר נמצאה, הופכת מיד לדליפה או שינוי נתונים.

תיקון נדרש: לצמצם grants לפי עקרון ההרשאה המינימלית ולהשאיר פעולות רגישות מאחורי RPC מבוקר.

### 11. שימוש ב־`search_path=public` בפונקציות בעלות הרשאות גבוהות

רוב הפונקציות משתמשות ב־`SECURITY DEFINER SET search_path=public`. זה טוב יותר מ־search path משתנה, אך עדיף `search_path=''` עם שמות מלאים לכל אובייקט. Supabase Advisor סימן גם את `set_updated_at` כבעל search path משתנה.

## ממצאים בחומרה נמוכה והקשחה

* שגיאות Supabase גולמיות מוצגות בחלק מהמקומות למשתמש ונרשמות ל־console. הן עלולות לחשוף שמות טבלאות, פונקציות ופרטי זרימה.
* לא נמצאה הגבלת קצב ייעודית ליצירת קבוצות, ניסיונות קוד הזמנה, רישום Push ופעולות RPC רגישות.
* קוד הזמנה קצר יחסית דורש הגבלת ניסיונות וניטור כדי לצמצם ניחוש.
* URL מתוך payload של Push נפתח על ידי Service Worker. כדאי להגביל אותו ל־same origin.
* CORS של פונקציית ההתראות הוא `*`. הפעולה הסודית מוגנת באמצעות secret, אך עדיף להגביל origins כאשר אין צורך בגישה מכל אתר.

## מה נמצא תקין

* לא נמצא `service_role` או מפתח פרטי מחויב ל־Git. `.env.local` מוחרג ולא נמצא בהיסטוריית Git.
* מפתח `VITE_SUPABASE_ANON_KEY` גלוי בכוונה ואינו סוד. אסור להכניס ל־frontend מפתח service role.
* לא נמצא שימוש ב־`dangerouslySetInnerHTML`, ב־`eval`, ב־`new Function` או ב־SQL דינמי.
* קריאות הלקוח ל־Supabase משתמשות בפרמטרים ולא בחיבור מחרוזות SQL. לא נמצאה נקודת SQL injection ישירה.
* RLS פעיל בטבלאות הציבוריות שנבדקו.
* זרימת הדירוגים הנוכחית מגבילה קריאה לדירוג העצמי וה־RPC של audit כולל בדיקות הרשאה.
* `045_fill_teams_to_configured_size.sql` משתמש בפרמטר UUID, בודק הרשאת `generate_teams`, נועל את המשחק, ואינו מכיל SQL דינמי. הוא גם שולל הרצה מ־`PUBLIC` ומ־`anon`. מומלץ בעתיד להקשיח את `search_path`, אך לא נמצאה בו פרצת injection.

## קוד בדפדפן

אי אפשר למנוע ממשתמש לראות JavaScript שנשלח לדפדפן, את מפתח ה־anon או את בקשות הרשת. build ממוזער ו־source maps כבויים כבר מקשים מעט על הקריאה, אך הם אינם מנגנון אבטחה. ההגנה האמיתית חייבת להיות RLS נכון, הרשאות SQL מינימליות, RPC עם בדיקות שרת, שמירת סודות מחוץ ל־frontend וניטור.

## סדר תיקון מומלץ

1. לחסום הסלמת `is_system_admin` ושדות פרופיל רגישים ולבצע בדיקת אירועים היסטורית.
2. לתקן מיד את מדיניות `activity_events`.
3. לסגור `notify_group`, `log_activity` וכל פונקציות הטריגר בפני API ציבורי.
4. לצמצם חשיפת פרופילים ולעצב API בטוח לכרטיס שחקן.
5. לפצל הרשאות עדכון בקבוצות ובמשחקים לפעולות ממוקדות.
6. ליישר את היסטוריית המיגרציות.
7. להוסיף בדיקות הרשאה אוטומטיות עם משתמשים משתי קבוצות ותפקידים שונים.
8. לעדכן dependencies, מדיניות סיסמה וכותרות Vercel.

## בדיקות קבלה לתיקון

* משתמש רגיל אינו יכול לשנות `is_system_admin`, `base_rating`, `lifecycle_status`, `archived_at` או מזהה פרופיל.
* משתמש בקבוצה א אינו יכול לקרוא פעילות, פרופילים פרטיים, משחקים, חברים או התראות של קבוצה ב.
* `anon` אינו יכול להריץ פונקציות פנימיות או ליצור פעילות והתראות.
* הרשאת `close_registration` משנה רק מצב הרשמה; הרשאת `open_ratings` משנה רק שדות דירוג; הרשאת שינוי שם משנה רק כותרת.
* מנהל קבוצה שאינו בעלים אינו יכול לשנות בעלות, קוד הזמנה או מצב מערכת.
* אין אזהרות High ב־`npm audit --omit=dev`.
* בדיקת Supabase Advisor חוזרת ללא פונקציות פנימיות חשופות וללא search path משתנה.
